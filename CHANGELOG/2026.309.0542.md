# 2026.309.0542 — refactor(krun): export the guest-kernel recipe as files/build-kernel.sh

## Summary

Exports the `libkrunfw-crabbox` guest-kernel recipe into `files/build-kernel.sh` — the ONE implementation — and makes the `layer-krun` candy install that script and run it, instead of carrying the recipe inline.

- **`files/build-kernel.sh`** — the recipe, unchanged in behavior: libkrunfw v5.6.2's own sources, patches and stock config, plus `config-libkrunfw-crabbox.fragment`, `make linux-6.12.109` + `olddefconfig` with every required option asserted, then `make vmlinux` only. Three parameters are lifted to environment variables with the previous values as defaults: `KRUN_KERNEL_CACHE` (`/var/cache/charly/krun-kernel`), `KRUN_KERNEL_FRAGMENT` (`/tmp/krun/config-libkrunfw-crabbox.fragment`) and `KRUN_KERNEL_DEST` (`/krun/vmlinux`).
- **`charly.yml`** — a new `copy:` step installs the script at `/usr/local/libexec/krun/build-kernel.sh`, and the `krun-guest-kernel` step runs it with the same `id`, `run_as` and `cache:` mount as before. The inline command block is deleted.
- **`AGENTS.md`, `README.md`** — name `files/build-kernel.sh` as the canonical recipe.

Why (R2): a downstream image repo needs this exact kernel, and the recipe existed only as candy task text, so the only alternatives were a verbatim copy or importing the whole host-side `layer-krun` candy (crun, libkrun, the host ICDs) into a guest image. With one script, the consumer fetches it from a pinned `layer-krun` tag the same way it already fetches the fragment.

### Static gate — `charly box validate`

Run with `CHARLY_PLUGIN_ONLY=1`, which is the documented way to stop a worktree binary from reaching the installed package's plugin directory. It removes the cause of the banner (a dev binary never loads those plugins), not the message: the resolution path is the project's own candy sources, and the validate counts are the same as an unmasked run. The absence of the banner is asserted, not assumed.
